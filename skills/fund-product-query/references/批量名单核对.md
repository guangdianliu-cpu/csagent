## 批量名单核对（清单 / 附件 / 一次问很多只）

### 适用场景
- 群里贴一列产品名问「这些是否代销 / 能不能买 / 费率多少」
- 用户发 Excel 附件（拟准入清单、白名单）问「这里面代销吗」
- 一次问 3 只以上

### 固定动作（两步，别自创第三步）
1. **`product_name_lookup` 一次把所有名字解析成代码**——名单有几只就一次全传进去，
   附件里的名字先用 `read_file` / 脚本读出「产品名称」那一列，**整列一次性传**
   （代码已在清单里就跳过这步，直接进第 2 步）
2. **`product_lookup` 按代码取数**，`fund_codes` 一次最多 30 只，
   **`aspects` 只要这一问真正用得上的那几项**：
   - 「是否代销 / 能不能买」→ `["basic"]`（要限额再加 `"limits"`）
   - 「费率 / 折扣」→ `["fees","discounts"]`
   - **名单类问题禁用 `aspects:"all"`**：`profile` 每只多 2 次后端调用，30 只就是 60 次

### 名单超过 15 只：出表发文件，别在正文里排 50 行

15 行以上的 Markdown 表格在企微手机端根本没法看。超过就走这条固定三步，
**不要自己 write_script 拼 openpyxl**：

1. `product_lookup` 加 `out_file`：`product_lookup(fund_codes=[...], aspects=["basic","limits"], out_file="funds.json")`
   ——完整结果落到本会话 outbound 目录，stdout 只回精简视图 + `saved_to`，
   上下文里永远只有摘要（多大的名单都不会再撞截断）
2. `product_make_report(source="funds.json", target="代销核对.xlsx")`
   ——一次出表，状态码已译成中文、天文数字已写成「暂无明确上限」
3. `send_file(path="代销核对.xlsx")`

**正文照样要给结论，不许只甩附件**：先一句「共 N 只，M 只可买，X 只未代销：AAA、BBB」，
再说明细见附件。客户要的是判断，文件是备查。

超过 30 只时 `product_lookup` 要拆批（单次上限 30），每批用不同的 `out_file`，
最后把多个 json 分别出表，或只对关键那批出表——拆批要连续发出，不要一批一轮。

`out_file` / `send_file` 都只认**裸文件名**，会话目录由系统注入，
不要自己拼 `data/uploads/...` 路径，也不要去查 session id。

### 硬性禁止（这几条各自都单独把线上打到超时过）
- **禁止逐只 `product_entity_query` 解析名字**。25 个名字发 25 次 `product_entity_query(fund_products, fund_name like ...)`，
  光名称解析就摊掉 6~8 个 ReAct 轮次和 40 秒，必撞 `max_rounds` / 整体超时。名字批量解析只走 `product_name_lookup`
- **禁止自己写脚本去包装查询**。批量、并发、分片这些工具内部已经做了；
  自写 wrapper 只会多花 2~4 轮
- **禁止自己写 openpyxl 脚本出表**。用 `product_make_report`，它已经处理了状态码翻译、
  金额上限话术、列宽和表尾口径说明；自己写一遍只会又慢又不一致
- **禁止用 `run_shell` / `run_script` 满盘找本 Skill 的脚本**。查询全部走 `product_*` 工具，
  不需要也不允许去查脚本路径
- **禁止把一份名单拆成多轮零散查**。拆批只在超过 30 只时发生，且应连续发出，不要一批一轮

### 结果处理
- `resolved`：拿 `fund_codes` 直接进第 2 步。里面的 `consign_flag` 只是搜索摘要，
  **对客结论以 `product_lookup` 的 `basic` 为准**；两者不一致时信 `basic`。仍是 `1` 才算代销，空/缺失=状态未返回
- `ambiguous`：该名字对应多只份额（用户没写 A/C），**不许替客户挑一只**，
  在回复里点名说明存在哪几只份额、请其确认
- `unmatched`：如实说未查到该产品，可附 `near` 里的相近名称供核对
- `dropped` / `truncated`：说明还有几只本次没查，不要假装整份名单都核对过了
- `failed`：这些代码的这几项是接口调用失败、没查到（报表里显示「查询失败」），不是「未代销」也不是「暂无数据」。
  只对这些代码再调一次 `product_lookup`；仍失败就在结论里点名「N 只暂时查不到」，总数核对里单独列出
- **`view: "compact"` / `"minimal"`**：结果过大时工具会自动降级成一只一行的视图，
  `funds` 从对象变成数组。**数据是完整的、一只都没少**，不是查询失败，别因此重查；
  只有在 `omitted_aspects` 里点名的字段（费率/折扣/业绩明细）才需要把代码缩到 5 只以内单独再查

### 回复要点
- 用一张表列出：产品名称、代码、是否代销、申购状态（问了限额再加限额列）
- 表后补一句总数核对：「清单 N 只，已核对 M 只，X 只未匹配」——数字对不上时必须显式说明
- 只陈述事实，不做推荐；答完即止
