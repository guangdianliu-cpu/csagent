# 上下文压缩机制

本文描述**一次请求的上下文如何组装与压缩**。存储分层、容量边界与后端配置见
[记忆模块说明.md](记忆模块说明.md)。

---

## 1. 组件

| 文件 | 职责 |
|---|---|
| `memory/token_counter.py` | `TokenCounter`：tiktoken 计数、按 Token 断句截断、模型窗口推断 |
| `memory/budget.py` | `ContextBudgetAllocator`：Tier 0~3 分层预算分配、水位线判定 |
| `memory/compactor.py` | `StructuredCompactor`：Checkpoint 生成与窗口内消息渲染 |
| `memory/compactor_cache.py` | Checkpoint 缓存后端：进程内 LRU / Redis |
| `memory/context_selector.py` | `QueryAwareContextSelector`：按当前 query 裁剪快照与工具流水 |
| `memory/prompt_layout.py` | `PromptLayoutOptimizer`：消息分层组装、工具 schema 确定性排序 |
| `react/loop.py` | 循环内的 Token 感知压缩与工具结果截断 |

---

## 2. 一次请求的组装顺序

```text
1) short_term.load / snapshot_store.load_tool_calls
2) budget_allocator.allocate(system_prompt, tools, recent, summary)
       → BudgetAllocation{tool_history_tokens, recent_history_tokens, summary_tokens, ...}
3) compactor.build_context(session_id, history, current_query, token_budget)
       → CompactedContext{summary_block, recent_block}
4) context_selector.select_tool_history（按 2) 的预算裁剪）
5) prompt_layout.sort_tool_schemas（工具 schema 按名排序）
6) prompt_layout.assemble_initial_messages(system, request,
       persistent_instructions, checkpoint_summary, dynamic_context)
7) ReactLoop.run(...)：循环内水位线压缩 + 工具结果截断
8) 回写：short_term.append / transcript.append /
       compactor.schedule_refresh（后台刷 Checkpoint）/ snapshot_store.append_tool_calls
```

---

## 3. Token 计数

`TokenCounter` 用 tiktoken。encoding 按 `tiktoken.encoding_for_model(model_name)` 取，
取不到回落 `cl100k_base`；tiktoken 不可用时回落字符估算 `_estimate_tokens`。

上下文窗口来自 `_MODEL_CONTEXT_LIMITS`：先精确匹配模型名，再按前缀匹配。
`chat.model_context_limit` 为 `0`（默认）时走这条自动推断，非 0 时直接采用该值。

方法：`count_text` / `count_messages`（含 role 开销）/ `count_tools` /
`truncate_to_tokens`（在自然断句处截断）/ `tokens_to_chars_estimate`。

---

## 4. 预算分配

以模型窗口 `L` 为基数：

```
total_budget     = L × compact_threshold      (0.80)
response_reserve = L × response_reserve_ratio (0.10)
available        = total_budget − system_tokens − tools_tokens − response_reserve
```

`available` 按优先级逐层分配，各层实际消耗不超过分配上限，**未用满的空间下放给下一层**：

| 层 | 内容 | 上限 | 下限 |
|---|---|---|---|
| 0 | System Prompt + 工具 schema | 固定开销，先扣除 | — |
| — | 最近工具调用 | `tool_history_tokens` = 600，固定配额，在按比例分层前先扣 | — |
| 1 | 最近对话 | 扣完工具流水后剩余的 `× 0.50` | `tier1_min_tokens` = 200 |
| 2 | 历史 Checkpoint | 上面用剩的全部 | — |

工具流水之所以排在按比例分层之前，是因为它是「这一轮之前做过什么」的唯一确定性
来源，被对话或摘要挤掉的代价远大于它占的那几百 token。

`should_compact(current_tokens)` 在 `current_tokens` 超过 `total_budget` 时返回 `True`。

---

## 5. Checkpoint 压缩

窗口外的历史由 LLM 压成结构化 Checkpoint，四段固定结构：

```
### 用户目标与状态
### 关键决策与已完成操作
### 涉及关键实体
### 未决事项与下一步
```

- 系统提示词优先读 `configs/prompts/compactor.md`（M3.2：摘要只记标识与来源指针，不复述具体数字），该文件缺失或为空时用
  `compactor.py` 内置的 `STRUCTURED_COMPACTOR_PROMPT`。
- 已有 Checkpoint 时做**字段级合并更新**，不是重新叙述，防止多次压缩逐轮退化。
- 生成走 `schedule_refresh()` 后台异步执行，每个 `session_id` 一把 `asyncio.Lock`。
- 结果存 `compactor_cache`，后端跟随 `chat.memory_backend`。
- 预算上限 `summary_max_tokens` = 400。

Checkpoint 注入时被包成一对 user/assistant 锚点消息，正文里明写它是有损压缩产物，
并规定与工具实时返回冲突时以工具返回为准。

---

## 6. 窗口内消息渲染

最近 `history_window`（4）条保留裁剪后的原文，规则两条：

1. **末条完整保留**，只受防御性天花板 `recent_latest_max_tokens`（8000 token）限制。
2. 其余消息的上限取「角色基准」与「预算均分份额」中更宽的那个，且不低于
   `recent_min_tokens`（80）。均分份额 = (Tier 1 预算 − 末条实际占用) ÷ 其余条数。

角色基准：`recent_user_max_tokens` = 400，`recent_assistant_max_tokens` = 600。

**摘要缺失时的关键词补充**：从窗口外消息里按与当前 query 的词元重叠打分，
`overlap ≥ keyword_min_overlap`（2）才入选，user 消息 ×3.0、assistant ×0.6，
命中同一领域实体再 +5.0；assistant 的长 dump 直接排除。取分最高的
`keyword_max_inject`（2）条，各截到 `keyword_max_snippet_tokens`（80），按原顺序注入。

---

## 7. 查询感知选择

**工具流水** `select_tool_history`：
`score = 重叠词元数 × 2.0 + timestamp / 1e10`（近期轻微加权），取前 `max_items` 条，
在 `tool_history_tokens` 预算内依次纳入。

> 原先这里还有一条「领域快照」`select_snapshots`。该层从未被写入过，已随 M0.2 删除；
> 背景见 [记忆模块说明.md](记忆模块说明.md) §1。

## 8. Prompt 布局

`assemble_initial_messages` 按 KV Cache 友好的顺序分层：

```
[system]  系统提示词
          ## 持久规则与背景知识   ← configs/rules.md
[user]    [早期对话历史 Checkpoint …]   ← 稳定锚点


[assistant] 已了解上述早期对话概要…
[user]    本轮用户问题：…              ← 动态尾部，本轮问题排最前
          此前对话与快照（仅供指代消解，不要当作本轮新问题）：…
```

工具 schema 由 `sort_tool_schemas` 按函数名排序，避免字典顺序波动导致前缀缓存失效。

## 9. ReAct 循环内

- 水位线 `compact_threshold`（0.80）触发 `_maybe_compact_history`，保留 system 与
  Checkpoint 锚点对，压缩中段。
- 工具结果超过 `react.max_tool_result_chars`（当前 30000 字符）时全文外置到
  `data/artifacts/`，上下文只留结构摘要 + `artifact_id`（M3.1）。
  外置失败才回落到硬截断。模型用 `read_artifact` 按页取回。
- `stall_guard` 限制重复调用与调用总次数；`react.max_rounds`（48）、
  `react.max_tool_calls`（80）、`react.overall_timeout_seconds`（1500，软截止，
  硬截止再加 240 秒宽限）为循环边界。网页与企微一致：企微不再单独设更短的上限，
  它的兜底超时排在 ReAct 硬截止之后。企微流式消息从首次推送起 10 分钟内必须结束，
  任务到 560 秒还没做完时先给这条消息收尾（提示结果稍后单独发送），任务照常跑完，
  终答改用主动消息发到原会话（群里在开头标上发起人 `@userid`，纯文字，不会提醒）。
- 预算感知（`react/budget.py`）：三项上限开局写进系统提示词；任一项用到 70% 时在
  当轮最后一条工具结果后提醒一次「收敛」，用到 90% 或只剩 2 轮时提醒一次
  「停止调用工具、直接作答」。到点的硬约束仍由软截止、`stall_guard`、`max_rounds` 执行。
- `react.dynamic_tool_selection` 为 `true` 时，首轮可见工具集按用户输入关键词裁剪。

## 10. 配置速查（`configs/base.yaml`）

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `chat.model_context_limit` | `0` | 模型上下文窗口；0 表示按模型名自动推断 |
| `chat.compact_threshold` | `0.80` | 压缩水位线比例 |
| `chat.response_reserve_ratio` | `0.10` | 预留给模型生成的窗口比例 |
| `chat.history_window` | `12` | 保留原文的最近消息条数（L0） |
| `chat.history_summary_enabled` | `true` | 是否启用窗口外 Checkpoint 压缩 |
| `chat.summary_max_tokens` | `4000` | L2 Checkpoint Token 预算 |
| `chat.max_history_messages` | `200` | 当前 episode 读窗口上限 |
| `chat.recall_window_days` | `180` | 跨段召回默认时间窗 |
| `chat.l1_max_tokens` | `200` | 单轮 L1 摘要预算 |
| `chat.l2_merge_every` | `8` | 每这么多条 L1 合并一份 L2 |
| `chat.history_summary_max_chars` | `800` | Checkpoint 字符上限 |
| `chat.recent_user_max_tokens` | `400` | 窗口内非末条 user 消息的角色基准 |
| `chat.recent_assistant_max_tokens` | `600` | 窗口内非末条 assistant 消息的角色基准 |
| `chat.tool_history_tokens` | `600` | 「最近工具调用」注入上下文的固定配额 |
| `react.max_tool_result_chars` | `8000` | 单条工具结果写入上下文的硬截断 |
| `react.dynamic_tool_selection` | `true` | 首轮工具集裁剪 |
| `react.max_rounds` / `max_tool_calls` | `48` / `80` | 单次循环上限 |
| `react.overall_timeout_seconds` | `1500` | 单次循环软截止（网页与企微相同） |

`recent_latest_max_tokens`（8000）、`recent_min_tokens`（80）、`keyword_max_inject`（2）、
`keyword_max_snippet_tokens`（80）、`keyword_min_overlap`（2）、
`tier1_ratio`（0.50）、`tier1_min_tokens`（200）
只在 `CompactorConfig` 与 `ContextBudgetConfig` 里，未提升为 YAML 配置项。
