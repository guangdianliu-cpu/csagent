# 记忆模块说明（`src/csagent/memory`）

各层职责、执行链路、容量边界与配置。上下文压缩的组装细节见
[上下文压缩、记忆系统.md](上下文压缩、记忆系统.md)。

当前只有**会话级**记忆，没有跨会话持久记忆：没有长期客户画像，也没有 Agent 自主经验沉淀。

---

## 1. 分层体系

| 层级 | 作用域 | 职责 | 实现 |
|------|--------|------|------|
| **Token 与预算** | 会话全局 | tiktoken 精确计数；分层动态分配预算 | `token_counter.py` + `budget.py` |
| **短期记忆** | `session_id` | user/assistant 文本轮次（写入截断 + LRU/TTL） | `sqlite_store.py` / `short_term.py` / `redis_store.py` |
| **对话记录** | `session_id` | 落盘的完整轮次，回填界面、不进提示词 | `sqlite_store.py` / `transcript.py` |
| **时间线分段** | `session_id` | 按静默间隔把无限时间线切成 episode，无 UI | `sqlite_store.py` |
| **产物清单** | `session_id` | 收发过哪些文件（永久登记，与磁盘可分叉） | `artifact_store.py` |
| **工具调用流水** | `session_id` | 最近若干次工具调用的轻量快照 | `sqlite_store.py` / `session_snapshot.py` / `redis_store.py` |
| **历史 Checkpoint** | `session_id` | 窗口外历史的结构化提炼（后台 LLM 异步刷新） | `compactor.py` + `compactor_cache.py` |
| **查询感知选择** | 单次请求 | 按当前 query 的关键词/实体，在预算内裁剪工具流水 | `context_selector.py` |
| **Prompt 布局** | 单次请求 | Cache Breakpoint 对齐 + 确定性 Schema 排序 | `prompt_layout.py` |

> **已删除的一层（M0.2，2026-09）**：原有「会话领域快照」层按 `session_id` + domain
> 保存各 domain 最近一轮的 `structured_data`。其写入方法 `update()` 从未被生产代码
> 调用过，供给恒为空，却占着 30% 的可分配预算；工具流水的预算还从它派生
> （`snapshots_tokens // 4 or 80`），被永久钉死在 80 token。整层已删除，工具流水
> 改用独立配额 `chat.tool_history_tokens`。

> **合并的两层（M1，2026-09）**：「短期记忆」与「对话记录」原本是两个各写各的 store
> ——前者在进程内 `OrderedDict`，后者在 `transcripts.db`。进程一重启，界面还能翻到
> 三天前的对话，模型却一问三不知，会对用户断言「本会话没发过文件」。
> `sqlite` 后端把两者合并成 `data/csagent.db` 的**同一批行**，只是读取口径不同：
> 界面读 `display_content`（人话），模型读 `content`（带工作区路径的富文本）。
> 这两种文本必须保持不同，理由见 `sqlite_schema.py` 的模块注释。

存储后端由 `chat.memory_backend` 统一切换，短期记忆、对话记录、工具流水同时跟随：

| 后端 | 重启 | 多 worker | 跨机 | 用途 |
|------|------|-----------|------|------|
| `sqlite`（**当前**） | 不丢 | 支持（WAL） | 不支持 | 生产默认 |
| `memory` | 失忆 | 不支持 | 不支持 | 本地开发与测试 |
| `redis` | TTL 到期即丢 | 支持 | 支持 | 跨机共享，**不是持久化方案** |

`configs/base.yaml` 的值**覆盖** `.env` 的 `MEMORY_BACKEND`，改后端只改 YAML。

升级说明：首次以 `sqlite` 启动时会自动把旧 `data/transcripts.db` 的对话迁进新库
（按时间间隔重新切成 episode）。迁移**可重入**，目标库非空即跳过；旧库只读不改，
可直接当备份留着。

`episodes` 表在 M2.2 增加了 `next_turn` 列，启动时自动 `ALTER` 并按已有 `turn_id`
回填。不回填的话号源会从 0 重来，新问题和几个月前的历史撞号、插到时间线中间去。

### 时间线分段（episode）

一个身份（人 / 群）只有一条无限长的时间线，没有「新建会话」按钮，用户侧完全无感。
分段是库内部的事：静默超过 `chat.episode_gap_hours`（默认 12 小时）就开新的一段，
给 Checkpoint 和将来的跨段召回一个天然范围。

> **默认只注入当前 episode。** 更早的内容靠 FTS5 召回（`chat.recall_window_days`，
> 默认 180 天），片段带日期前缀。隔夜回来问「接着昨天那个」时，窗口是空的，
> 召回把带日期的旧片段捞回来。

### 并发定序（M2.2）

同一身份的并行提问**不串行化**（企微侧本来就能连发，串行等于凭空加延迟），
改为在请求**到达时**就从所在 episode 的号源取一个 `turn_id`，并把到达时刻记进
`messages.created_at`。读取按 `created_at` 排序，于是历史按「谁先问」排，
而不是「谁先跑完」——先问的那句若多调了两个工具，回写会晚几十秒。

两处容易忽略的配套：

- L1 读缓存里连**到达时刻**一起存，乱序落库时重排。只按追加顺序排的话，同一个
  会话在重启前（读缓存）和重启后（读库）会给出两种顺序。
- 工具流水写在本轮 `messages` **之前**（Checkpoint 刷新要先读到它），所以必须把
  凭据透传进 `append_tool_calls`，否则流水会挂到上一轮去。

过载保护是另一回事，在网关侧：`chat.max_concurrent_requests` 限制同时在跑的请求数，
满员时先回一句「已排队」再等名额。不静默等待——看不到反馈的用户会重发，
那正好再多占一个名额。

## 3. 一轮对话的执行链路

对应 `agent.py`：

```text
用户消息
│
├─ 1) 输入护栏（InputGuard）
├─ 2) 加载：short_term_memory.load / snapshot_store.load_tool_calls
├─ 3) budget_allocator.allocate(...)      → 各层 Token 预算
├─ 4) compactor.build_context(...)        → Checkpoint 块 + 最近对话原文块
├─ 5) context_selector.select_tool_history（按预算裁剪）
├─ 6) prompt_layout.sort_tool_schemas
├─ 7) ReAct 循环：动态工具裁剪 → 水位监控对齐压缩 → 工具结果截断
└─ 8) 回写（_write_back_memory）：
      ├─ short_term_memory.append(user, assistant)        【写入即截断】
      ├─ compactor.schedule_refresh(...)                  【后台异步刷 Checkpoint】
      └─ snapshot_store.append_tool_calls(...)
```

第 8 步在 `finally` 里执行（M0.1）：客户端中途断连时，已经流给用户的半截回答
同样要落盘并打上「未完成」标记，否则屏幕上留着文字、模型侧零记录，下一轮会否认
自己说过话。见 `agent._finalize_interrupted_turn`。

### 界面回填：对话记录

`Agent.load_history(session_id)` → `GET /api/chat/history` → `static/index.html` 的
`loadHistory()`，用于浏览器刷新后把聊天区铺回去。

`sqlite` 后端下它和模型记忆是**同一批行**，区别只在读取口径和取多少：

| | 模型口径 | 界面口径 |
|---|---|---|
| 读哪一列 | `content`（富文本，带工作区路径） | `display_content`（人话，空则回落 `content`） |
| 进提示词 | 进 | **不进** |
| 一次取多少 | `max_history_messages` = 20 条 | `transcript.max_return` = 100 条 |
| 活多久 | 落盘，默认永不删除 | 同左 |

由此：**屏幕上能翻到的 ≠ 模型还记得的**——但这现在只是"取多少"的差别，不再是
"存不存在"的差别。窗口外的内容模型只剩 Checkpoint 摘要。

两种口径同在 `_write_back_memory` 一次写入（`append_turn`），落库失败只告警不抛。

数据源不复用审计侧 `data/audit/sessions-*.jsonl`：它按天分片、无索引、可被
`AUDIT_LOG_ENABLED` 关掉。

## 4. 容量边界

应用侧只能限制单个会话写多少；会话总数的上限取决于后端。

| 对象 | 上限 | 位置 |
|------|------|------|
| 单条消息字符数 | `max_message_chars` = 8000，超出截断并标记 | `short_term.clip_message` |
| 每会话**注入**消息条数 | `max_history_messages` = 20 | 各后端读窗口时 trim |
| 每会话工具流水条数 | 50 | `session_snapshot.py` |
| 单条工具结果预览 | 500 字符 | `react/loop.py` 写入时截断 |
| **会话总数（sqlite 后端）** | 无上限；`max_sessions` 只限 L1 读缓存 | `sqlite_store.py` |
| **会话总数（memory 后端）** | `max_sessions` = 2000，OrderedDict LRU | 三个进程内 store |
| **会话总数（redis 后端）** | 无上限，只靠 TTL（86400s）过期 | — |

`sqlite` 后端下「存多少」和「注入多少」彻底解耦：库里按轮次一直追加（默认永不删除），
每轮只读最近 `max_history_messages` 条进上下文。所以库变大不会推高单轮 Token 成本——
膨胀的代价体现在检索噪声上，由召回窗口治理（设计文档 M2.3）。

`max_message_chars` 必须 ≥ 读取侧末条消息天花板 `recent_latest_max_tokens`（8000 token）
能吃下的量。中文约 1 字 ≥ 1 token，8000 字符即已覆盖；英文占比高的流量需上调到 32000。

### 进程内后端的限制（M1 之前的默认，现仅用于本地开发）

1. **无时间过期**。只有 `max_sessions` 计数 LRU，没有 TTL，僵尸会话持续占坑位。
2. **容量硬上限 = `max_sessions`**（2000）。三个 store 各自独立计数、淘汰不同步，
   会出现「历史还在但工具流水没了」的错位状态。
3. **内存压在 Python 进程堆**，pydantic 对象开销约为 Redis 紧凑编码的 2~3 倍，RSS 基本只涨不落。
4. **重启丢光**会话历史、工具流水与 Checkpoint。
5. **不支持多进程**。加 uvicorn workers 或横向扩展后，同一用户的连续请求落到不同进程，
   记忆会随机消失。
6. **不可观测**。没有等价于 `sqlite3 data/csagent.db` 或 Redis `SCAN` 的手段。

切到 `sqlite` 后 1/2/4/5/6 均已消除，3 只剩 L1 读缓存那一份（受 `max_sessions` 约束）。

### SQLite 后端的边界

覆盖**单机多 worker**：WAL 让读不阻塞写，`busy_timeout=5000` 让并发写"慢一点"而不是
报 `database is locked`。

**不覆盖跨机多实例**——网络文件系统上的锁不可靠。真到那一天需要换 Postgres。
所有存储访问都走 `protocols.py` 的协议、由 `factory.py` 按配置选实现，届时新增一个
后端实现即可，调用方零改动。不要因为「可能多实例」现在就上 Redis：它解决不了重启
失忆（TTL 缓存），等于付了运维成本却没拿到主要收益。

## 5. Redis 后端（当前未启用）

### 服务端必须配 maxmemory

Redis 后端没有会话数上限，全局兜底只能落在服务端：

```conf
maxmemory 2gb                    # 单位：Redis 里 2gb = 2×1024³，2g = 2×1000³
maxmemory-policy volatile-lru    # 所有 key 都带 TTL
```

两个默认值都不可用：`maxmemory=0` 不限，内存涨到宿主机 OOM；policy 为默认 `noeviction`
时写满后写入报 OOM 错误，表现为会话读得到却写不进去。

**容量测算**（按 §4 各项上限反推，单会话）：

| 组成 | 最坏 | 典型 |
|------|------|------|
| `stm` 20 条 × 8000 字符（中文 UTF-8 3B/字） | 480KB | ~30KB |
| `snap` 8192 字符 × domain 数 | ~25KB | ~8KB |
| `snap:tools` 50 条 | ~30KB | ~15KB |
| `summary` 800 字符 | ~2.4KB | ~2.4KB |
| **合计** | **~540KB** | **~55KB** |

2GB 可容纳 TTL 窗口（24h）内约 3,900（全长回复）~ 38,000（典型）个活跃会话。
以 `INFO memory` 的 `used_memory_peak` 为调整依据。

### 生产配置（Linux + Redis 5.x，本项目专用实例）

| 项 | 值 |
|----|----|
| `requirepass` | 强密码。`csagent:stm:*` 是用户对话原文；bind 内网地址后 `protected-mode` 失效 |
| `bind` | 内网地址 + 127.0.0.1（留空 = 监听所有接口） |
| `REDIS_URL` | `redis://:<密码>@<host>:6379/0` |
| `vm.overcommit_memory` | `1`，否则内存吃紧时 BGSAVE 的 fork 会失败 |
| THP | 关闭 |

Redis 5 的两个限制：无 ACL（6.0 才有），只有 `requirepass` 一个全局密码；
`CONFIG GET` 只接受单参数，`check_memory_policy` 因此拆成两次调用。

若按常规加固禁用或重命名 `CONFIG`，`check_memory_policy` 会静默跳过（降级 debug 日志）。
专用实例 + `requirepass` + `bind` 的前提下，保留 `CONFIG` 可用。

**Windows 版特有**（开发机 tporadowski redis 5.0.14，生产 Linux 不适用）：

1. 该 fork 用系统页面文件分配堆内存模拟 `fork()`；不设 maxmemory 时会在触到堆上限后
   抛 OOM 异常终止。
2. 开着 `save`（RDB）时 BGSAVE 期间提交内存显著高于 `used_memory`，maxmemory 要留一倍余量。
3. 任务管理器 / ProcessExplorer 的 Working Set 不准，以 `INFO memory` 为准。

启动时 `check_memory_policy` 探测并告警（`redis_maxmemory_unbounded` /
`redis_eviction_policy_unsafe` / `redis_memory_policy_ok`），不拦启动；
可用 `REDIS_MEMORY_POLICY_CHECK=false` 关闭。

### Key 布局

| Key | 类型 | 内容 |
|-----|------|------|
| `csagent:stm:{sid}` | List | 短期消息，`ltrim` 到 20 条 |
| `csagent:snap:{sid}` | Hash | field=domain，value=快照 JSON |
| `csagent:snap:tools:{sid}` | List | 工具调用快照，`ltrim` 到 50 条 |
| `csagent:summary:{sid}` | String | Checkpoint |

全部带 TTL，每次写入都 `expire` 刷新（滑动过期）。

## 7. 已知缺口

- `compactor._locks` 每 session 一把 `asyncio.Lock`，只增不删。
